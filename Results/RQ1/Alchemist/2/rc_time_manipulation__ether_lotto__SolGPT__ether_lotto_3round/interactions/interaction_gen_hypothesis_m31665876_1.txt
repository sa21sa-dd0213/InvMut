Let’s analyze the difference.  

The original contract uses `keccak256` to generate pseudo-randomness. The mutant replaces `keccak256` with `sha256`. Both are hash functions, but they produce different outputs for the same input. Since the game outcome depends on `hash % 2`, the result will sometimes differ between the two hash functions for the same `block.timestamp` and `block.difficulty`.  

A test that always passes on the original but fails on the mutant would need to exploit a scenario where the outcome flips due to the different hash function. However, we cannot control the block’s difficulty or timestamp in a predictable way inside a single transaction.  

But we *can* rely on statistical probability: if we run the `play` function many times with different block data (by mining blocks between calls), the distribution of wins/losses will be identical *on average* for both functions, so a single test expecting a specific outcome won’t reliably kill the mutant.  

What can reliably differentiate them?  
- The mutant uses `sha256`, which returns `bytes32`. The original uses `keccak256`, which also returns `bytes32`.  
- The critical difference: `sha256` is not an EVM-native precompile with the same gas cost as `keccak256`. Calling `sha256` costs more gas.  

Therefore, **a test that measures gas consumption of the `play` function** will detect the mutant because the gas cost increases when `sha256` is used instead of `keccak256`.
